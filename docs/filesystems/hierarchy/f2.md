# F2: the mount manifest and its policy

Phase F2 of [implementation-phases.md](implementation-phases.md). Its
definition of done: required and optional mount failures behave differently by
policy; no wrong-volume fallback; mount and unmount with open descriptors are
tested. Where it starts is [inventory.md](inventory.md): every mount today is
a line of kernel code, the root is found by label and the ESP becomes the root
when it is not, other volumes land at `/vol<N>` in the order the scan found
them, and there are no mount options.

[integration.md](integration.md) has init mount the volumes. Nothing in
userland can yet: there is no `mount` call and no filesystem manager. So F2
puts the manifest and its policy in the kernel, where the mounts are, behind an
interface a userland manager can take over later; the `mount`/`umount2` calls
are the step where that starts.

## Steps

Each step is one commit, verified as every step here is: host tests, the
sabotage cases that prove them, six boots.

1. **Stable volume identity.** The storage scan records what identifies each
   volume across boots and disks: ext4's UUID and label, FAT's volume serial
   and label, exFAT's and NTFS's serial, a GPT partition's GUID. The boot log
   and `/proc/mounts` say them. The oracle is the host's `blkid`, run on the
   images the build makes - not a number this project computed twice.

2. **The root by identity, never by fallback.** The build writes the root's
   UUID to the ESP (`EFI/VIBEOS/ROOT`, one line: `UUID=...`), the way a boot
   loader's configuration names its root. The kernel mounts the volume with
   that UUID as `/`. Not found: the boot says so and stays on the ESP as a
   rescue root - never another volume that happens to be ext4. No `ROOT` file:
   the bring-up layout (a bare ESP), said in the log, as today.

3. **The manifest.** `/etc/vibeos/mounts`, read from the root once it is
   mounted: a version line, then one mount a line - what (`UUID=`, `LABEL=`,
   or a pseudo filesystem's name), where, the filesystem, its options, and
   `required` or `optional`. `/tmp`, `/run`, `/dev/shm`, `/proc`, `/dev` and
   `/boot/efi` come from it, not from code. A required mount that fails is a
   named failure the boot gate reports, and the boot carries on in a rescue
   state with what it has; an optional one is logged and nothing else. A
   volume no line names is not mounted - `/mnt` is not an automount
   namespace - and `/vol<N>` goes. A manifest that does not parse is refused
   whole for the built-in default (today's mounts), loudly: a typo must not
   take the root's mounts away. Bounded: each device is waited for a fixed
   number of times.

4. **Mount options**, kept in the mount and enforced where they mean
   something: `ro` (every writing operation EROFS), `noexec` (exec EACCES),
   `nodev` (opening a device node EACCES), `nosuid` (exec ignores the set-id
   bits). Reported by `/proc/mounts` and by statfs's flags (`ST_RDONLY`,
   `ST_NOSUID`, ...). `/tmp` and `/dev/shm` are `nosuid,nodev`; `/boot/efi`
   is `ro` on a production root and read-write on the gate's media, which
   writes to it on purpose - the manifest says which.

5. **Unmount with descriptors open.** A mount counts the open descriptions on
   it; detaching a busy mount is EBUSY, as Linux's umount without
   MNT_DETACH. Host tests open, unmount, close, unmount; and a descriptor kept
   across a refused unmount still reads.

6. **`mount` and `umount2` for programs** (the Linux calls, root only, the
   options above), so the administrator - and later a userland manager - can
   mount what the manifest does not.

Per-service credentials and capability checks on mounts, which the phase table
also names, belong to the security milestone (next-steps.md item 5).

## Status

Step 1: done 2026-11-18. Each driver reads its volume's identity after
mounting it (`identify` in `vibeos_fs_driver_t`): ext's UUID and label, FAT's
serial and label, exFAT's and NTFS's serial, ISO9660's creation date and
volume id. The boot log's `[IO] VOLUME` line says them. `verify-volid.py`
holds them to blkid on eight images the host's own tools made (ext4, ext2,
FAT16, FAT32, FAT with no label, exFAT, NTFS, ISO9660), and the boot gate
holds the root's UUID to blkid's reading of the image the guest left
(`volume_uuid_wrong`). `fs-volid.txt`, `fs-volid-drivers.txt` and
`fs-volid-boot.txt` go red six ways. Not read: exFAT's and NTFS's labels
(a directory entry and an attribute), and a GPT partition's GUID - nothing
names a volume by them yet.

Step 2: done 2026-11-18. The root is named by UUID, not by label: the boot
disk's writer puts `UUID=<blkid's uuid>` in `EFI/VIBEOS/ROOT` on the ESP, and
`vibeos_storage_pick_root` finds the mounted volume carrying it - matched
case-insensitively, refused as ambiguous when two volumes share it, and never
a fallback to "the first ext4". The boot log says `[IO] ROOT by=uuid
result=...`; the gate fails `root_not_found_by_uuid` and
`native_root_not_mounted`. `fs-root-pick.txt` (five host cases) and
`fs-root-boot.txt`/`ext4-root-boot.txt` go red.

Step 3: done 2026-11-18. The kernel reads `/etc/vibeos/mounts` from the root
(`kernel/fs/mounttab.c`, portable and host-tested) and mounts what it names:
the ESP by `UUID=` at `/boot/efi`, `/tmp`, `/proc`, `/dev`, `/run` and
`/dev/shm` as pseudo filesystems, with `mode=` and `size=` for a tmpfs.
`make-boot-disk.py` writes the file, the ESP's line copied from blkid. A line
is `what where type options required|optional`; `LABEL=` works too, a label
with a space cannot be written. The parse is all or nothing: a manifest that
is missing or refused is the built-in default (the same mounts, the ESP as
"the volume the machine booted from", optional), said as `[IO] MOUNTS
source=default|refused why=... line=...`. A required line that fails is
`[IO] MOUNT_REQUIRED_FAILED`, the boot goes on as a rescue state and the gate
fails `required_mount_failed`; the gate also fails `manifest_not_from_root`
and `esp_not_mounted_by_uuid`. A volume no line names is not mounted:
`/vol<N>` is gone. Options are parsed and kept, unknown ones refuse the
manifest; enforcing them is step 4. Not done: waiting for a device - the
scan is synchronous and sees every disk the boot sees, so there is nothing to
wait for yet. Cases: `fs-mounttab.txt` (ten host), `fs-manifest-boot.txt`
(three boot), the label case in `fs-root-pick.txt`.

Step 4: done 2026-11-19. A mount carries its options (`flags` in
`vibeos_fsmount_t`, `VIBEOS_MNT_*` in vfs.h), set from the manifest line when
it is attached. `ro`: every writing wrapper in the VFS is EROFS before the
filesystem is asked - the kernel's own writes through them included - and
`vibeos_fs_writable` says no, so open for writing and access(W_OK) refuse
too; the unlink handler passes EROFS on instead of turning every refusal into
EIO. `noexec`: execve is EACCES, the superuser included. `nodev`: a device
node does not open (EACCES); no filesystem here can make one yet, so the test
makes `/dev` itself nodev. `nosuid`: nothing to enforce - this kernel honours
no set-id bit at all - so it is kept and reported. `/proc/mounts` prints
`rw|ro[,nosuid][,nodev][,noexec]` and statfs's `f_flags` carries
`ST_RDONLY|ST_NOSUID|ST_NODEV|ST_NOEXEC` (compared with the host's by the
layout test); a driver's statfs no longer overwrites what the mount says.
`/boot/efi` stays `rw` on every image: the gate writes to it on purpose and
the VM images have not been tried read-only - a production manifest that
makes it `ro` belongs with the installer. Not enforced: noexec for an mmap
with PROT_EXEC and for the interpreter a program names, and for the native
(non-Linux) exec path. Cases: `fs-mount-ro.txt`, `fs-mount-exec.txt`,
`fs-mount-nodev.txt` (host), `fs-mount-report.txt` (boot); the gate fails
`mount_options_not_reported`.

Step 5: done 2026-11-19. `vibeos_fs_umount(path)` takes a mount out of the
table as Linux's umount without MNT_DETACH: EINVAL when nothing is mounted
exactly there, EBUSY while a description stands on it or another mount lies
beneath it, and a refusal changes nothing - the descriptor that kept it busy
still reads. Busy is asked of the open-file table (`file_mount_busy`,
registered as the node-open query is) rather than counted beside it: every
description already names its mount, and a second record is one more thing to
disagree. The same entry or the same driver state counts, because the root is
attached as a copy of the scan's mount. Host test `t_umount_busy`: open,
unmount refused, read, close, unmount, unmount again refused. Not busy yet: a
process's working directory on the mount, an inotify watch and a bound unix
socket, which Linux counts too - `cwd` is a path here, not a reference. The
check and the removal are one critical section, but an open that has resolved
the mount and not yet made its description can still slip past an unmount; the
mount itself stays valid (the caller owns it), so such a description works on
a detached mount as MNT_DETACH would leave it. Cases: `fs-umount.txt`,
`fs-umount-busy.txt`. Nothing calls it on the machine until step 6.

Step 6: done 2026-11-19. `mount` (165) and `umount2` (166), the
superuser's (EPERM for anybody else). A mount is a manifest line built from
the arguments - source, the target's absolute path, type, the data as
options plus `ro`/`nosuid`/`nodev`/`noexec` from MS_* - and judged by the
manifest's own parser (`vibeos_mounttab_parse_line`), so a program's mount
obeys the boot's rules; the machine mounts it as it mounts a manifest line
(`ks_mount` -> `hw_mount_one`). The source is a volume's `UUID=`/`LABEL=` or
anything at all for tmpfs, proc and devtmpfs; a device path names no volume
(there are no block device nodes) and is ENODEV for a disk type, a UUID nobody
carries ENOENT, a taken place EBUSY, a full tmpfs pool ENOMEM. `umount2` is
step 5's unmount (`ks_umount` -> `hw_umount_one`), and gives back what a
pseudo filesystem held so it can be mounted again; a volume stays mounted
where the scan made it, only unreachable. Refused rather than pretended:
MS_REMOUNT, MS_BIND, MS_MOVE and propagation (EINVAL), MNT_FORCE, MNT_DETACH
and MNT_EXPIRE (EINVAL) - the two gaps the registry lists. The mount table
holds 32 (it was 8, which the manifest and the I/O self-test already filled),
the tmpfs pool four instances, reused once unmounted. The shell self-test
runs BusyBox's `mount -t tmpfs` on `/mnt`, writes through it and unmounts it;
the gate fails `mount_syscall_failed` and `umount_syscall_failed`. Cases:
`fs-mount-syscall.txt` (host), `fs-mount-boot.txt` (boot).

F2's definition of done: required and optional failures behave differently
(step 3), no wrong-volume fallback (step 2), mount and unmount with open
descriptors tested (steps 5 and 6). What F2 leaves: per-service credentials
and capability checks on mounts (security milestone), cwd, inotify watches
and bound sockets keeping a mount busy, noexec for mmap and interpreters, and
a read-only `/boot/efi` on production images.
