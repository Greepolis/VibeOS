A user **stack** buffer whose first sixteen bytes the kernel read as zero. `interleaved_lines` is not at fault - its docstring already states the limit that let this through - so a separate check names the mechanism now ([mm_ring3_write_nul.md](implementation_progress/mm_ring3_write_nul.md)). **Narrowed hard**: the copy-on-write copy is faithful (a fold of the page before and after every resolution, `cow_copy_changed=0`), the page faults several times in the same process rather than once as a comment in the tree claimed, and the defect **needs more than one core** - eight boots at `-smp 1` produce zero corrupted writes against three to five in ten at four. The process migrates, measured on both sides. The explanation that fits every symptom - a stale writable TLB entry surviving a fork that sent no shootdown because the process is single-threaded - is **refuted by one grep**: there is no PTE_GLOBAL and no CR4.PGE in this tree, so every CR3 write flushes. The mechanism is open and the candidate list is written down ([mm_lost_store_smp.md](implementation_progress/mm_lost_store_smp.md)). Four explanations for the **argv** defect were instrumented and closed on the way - the desktop's buffer cannot reach the low user window (`pmm_reserve` truncates the region), the framebuffer is outside managed RAM, a canary shows no overrun, and no frame of it is shared or lost - and the question that file named as its next step was already answered by `double_allocs`, a counter nobody had connected to it. The argv defect **did not reproduce in eighteen boots** against a recorded rate of one in six. **ROOT CAUSE FOUND AND FIXED**: the kernel set CR4.OSFXSR, uses **6955** XMM instructions of its own, and contains **zero** `fxsave`/`fxrstor`/`xsave` - so a user task's SSE registers survive a syscall, an interrupt or a context switch only by luck. clang stores 16-byte stack buffers with `movdqa`, which is why the corruption was **always exactly sixteen bytes** - one XMM register - a width nothing in the memory manager could explain. The zeros are not a fresh page: svc-stress forks a hundred children running a binary that opens with `pxor %xmm0,%xmm0`. And it explains the argv vector too: `COL_TITLETXT` is 0x00FFFFFF, the desktop paints from the kernel on interrupts, and a vectorised fill leaves two white pixels in a lane pair that the resumed task stores into its own buffer - the desktop never touches that memory, which is why every memory counter read zero and was right. Ten hypotheses were measured and killed first, all of them in the memory manager because the symptom looked like memory ([mm_no_fpu_context.md](implementation_progress/mm_no_fpu_context.md)). **Fixed, in two halves.** The context switch saves and restores a 512-byte per-task area (eager, not lazy: CR0.TS needs a fault handler, per-core ownership and cross-core invalidation, three mechanisms on the path this kernel has the most defects in); the initial state is built by hand because MXCSR at offset 24 reads zero as *unmask every SSE exception*; fork copies it, threads get a clean one, and CR4.OSFXSR is set on the boot processor too - only ap_boot.S ever set it, so the BSP had it because UEFI leaves it on. That half alone took the corruption from three boots in ten to **one in twelve**, which is the number that would have been called a fix on a five-boot sweep. The second half is `-mno-sse` on the kernel, as Linux does: a syscall returning to the same process never reaches the scheduler, so nothing saves anything. **22 boots: 0 corrupted writes, 0 xmm lost**, host tests and boot gate green. One near-miss recorded: the first attempt gated the flags on `if(IMAGE AND NOT TESTS)`, and both are on in every real build - it would have compiled to nothing while looking like a fix. **Open**: the argv vector that is not a pointer reads `0x00ffffff00ffffff` - two white pixels, `COL_TITLETXT` from the GUI - and the same value turned up independently as an out-of-range sector in the block layer. The desktop is painting over memory somebody else owns, which is a recurrence of a defect the code comments already describe, and it explains why every memory counter is zero: nothing is freed early, frames are handed out twice ([mm-argv-poison.txt](../scripts/dev/cases/mm-argv-poison.txt)). Two detector defects were fixed on the way: the mapper count was a global two cores overwrote, and the free-side check samples one free in sixteen, so its zero was being read as evidence. |

## Notes

- Status reflects code currently present in repository, not only planned milestones.
- A file existing under `user/compat/` is not progress. The Windows and macOS
  translators are twenty-four lines each, know two syscall numbers, and nothing
  calls them; they are tracked as not started for that reason. The Linux
  compatibility that works is the kernel syscall layer, which is a different
  piece of code entirely.
- "Verified" here means a gate fails if it regresses, unless the entry says otherwise. The framebuffer desktop is the standing exception: its serial-visible state is gated, its pixels are checked by hand with `scripts/dev/screenshot.py`.
- Each macro-area file contains:
  - implemented items verified in code
  - pending items
  - next execution checkpoint
