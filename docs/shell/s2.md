# S2: login

Phase S2 of the shell ([design.md](design.md)). Who is at the terminal, before
a shell runs. Done 2026-11-21.

## What there is

- **The accounts.** `/etc/passwd`, `/etc/group` and `/etc/shadow` (0600), with
  `root` and one user, `vibe` (1000, `/home/vibe`, 0700). The hash is
  sha512-crypt (`$6$`), which musl's `crypt` and the host's agree on; yescrypt,
  the design's other option, is not in musl.
- **Two kinds of image, decided 2026-11-21.** A development image - the boot
  gate's - has the known password `vibeos`, a fixture in
  `scripts/make-root-tree.py`. A **production** image has none: both accounts
  hold `!firstboot`, which no password can match, and login asks for them
  (eight characters at least, twice) before anybody can log in.
- **`login`** (`user/login/login.c`, static against musl, `/usr/bin/LOGIN.ELF`)
  is init's one service on a production root. It stays the parent of each
  session and asks again when the shell ends, so `exit` is a logout. A session
  is its own: `setsid`, the terminal made its controlling one, the user's
  groups and ids - checked afterwards, including that root cannot be taken
  back - the home directory, and a clean environment.
- **Refusals say nothing.** A name that does not exist costs the same hash and
  gets the same answer as a wrong password, the comparison looks at every byte,
  and a failure waits two seconds.
- **The password is written whole.** Beside the file, fsynced, renamed over it,
  and the directory fsynced: a power cut leaves the old shadow or the new one.
- **`/usr/bin/sh`** is a link to BusyBox, the name a login shell starts under.
  The other names in `/usr/bin` are S3's.

`/etc/shadow`'s mode and the home's owner are set in the image by
`make-boot-disk.py`, not left to the build tree: on a Windows disk mounted into
WSL every file reports 0777, and `mkfs.ext4 -d` would have copied that.

## How it is checked

- **`LOGINT.ELF`** plays the person through a pseudo-terminal on every boot: a
  wrong password, a name that does not exist, the password not echoed, the
  right one, the session's ids, home and environment, `/etc/shadow` out of a
  user's reach, a logout, root. The gate fails `login_failed:<which>`.
- **`scripts/dev/verify-first-boot.py`** boots a production image and types at
  its keyboard: both passwords set, a too-short one and a wrong one refused,
  a login; then the power is cut, and the second boot must not ask again and
  must take the same password. CI runs it on the `.vdi`.
- Cases: `login-boot.txt`.

## Not done

No `passwd` to change a password afterwards, no `su` or `sudo`, no account
lockout, no `utmp`/`wtmp`, and login runs on one terminal: the console. A root
that has `!firstboot` and nobody at the keyboard waits there. Password policy
beyond the length, and everything else about privilege, is the security
milestone's (next-steps.md).
