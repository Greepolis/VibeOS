# S3: the names in /usr/bin

Phase S3 of the shell ([design.md](design.md)), closing E4-021. Done
2026-11-21.

The ESP keeps its 8.3 names, which the firmware and the build need. On the root
a program now has the name the programs around it expect:

| What | Where |
|---|---|
| BusyBox | `/usr/bin/busybox` |
| Each of its applets (`sh`, `ls`, `cat`, ...) | a link in `/usr/bin`, from what `busybox --list` says this build has |
| login | `/usr/bin/login`, ours and not BusyBox's applet |
| init | `/usr/lib/vibeos/init` |
| Everything else in `EFI/BOOT`: the native `SH.ELF`, `CAT`, `LS`, `ECHO`, `WC`, the `SVC_*`, the gate's test programs | `/usr/lib/vibeos/test/`, on a development root only |

The layout is a list of what is the system's (`SYSTEM_PROGRAMS` in
`scripts/make-root-tree.py`), so a new test program stays out of production
without anybody having to remember. `vsh` will join `/usr/bin` in S4, the one
native program with a short name.

The gate asks the guest how many names in `/usr/bin` are a build's, what `ls`
is and where `which` finds `sh` (`usr_bin_names_wrong`, `names-boot.txt`).
`verify-first-boot.py` reads a production root's partition with debugfs: the
system's programs are there, and `/usr/lib/vibeos/test` is not.
