# S6: cmd

Phase S6 of the shell ([design.md](design.md)): Wine 9.0's `cmd.exe`, run by the
NT personality.

| Step | What | State |
|---|---|---|
| 1 | msvcrt: the wide-string calls cmd uses | done |
| 2 | cmd's own entry point, in place of mingw's C runtime start | done |
| 3 | The rest of msvcrt: `_wfopen`, `fgetws`, `feof`, `iswctype`, `sprintf` | done |
| 4 | kernel32: console, environment, dates, file operations | done |
| 5 | advapi32, user32, ntdll, and a small shell32 | done |
| 6 | cmd at boot, against what it prints under Wine | done |

Measured on 2026-11-22, cmd imports about 78 functions our DLLs do not export:
kernel32 36, msvcrt 33, advapi32 3, shell32 3, user32 2, ntdll 1. Some of the
msvcrt ones are only mingw's start-up code, which is what step 2 removes.

## Step 1

`towupper`, `_wcsupr`, `_wcslwr`, `_wcsrev`, `wcscspn`, `wcstol`, `wcstoul` and
`_wsplitpath`, in `user/win/msvcrt/crt_core.c`. The number parsers are compared
with glibc's on random strings, clamped to msvcrt's 32-bit `long`. A recent glibc
reads C23's `0b` prefix and msvcrt does not, so those strings are left out of the
comparison. Case: `win-msvcrt-cmd.txt`.

## Step 2

`user/win/cmd/entry.c` calls `wmain` and `ExitProcess`, and nothing else: cmd reads
`GetCommandLineW` itself and never looks at its `argv`. Built with `-nostdlib` and
`__USE_MINGW_ANSI_STDIO=0`, so neither mingw's start-up code nor its printf comes
along. That takes what cmd lacks from 78 functions to 48: kernel32 34, msvcrt 5
(`_wfopen`, `feof`, `fgetws`, `iswctype`, `sprintf`), advapi32 3, shell32 3,
user32 2, ntdll 1.

`GetCommandLineW` first ran with cmd itself, at step 6.

## Step 3

cmd opens one kind of stream: `_wfopen(name, "rt,ccs=unicode")`, for `FOR /F`.
That is the only mode `_wfopen` accepts here; any other is refused. The file is
read whole, and the decoder is in `crt_core.c` so the host tests it. Its rules were
asked of Wine's msvcrt on the same bytes: a BOM says UTF-8 or UTF-16, none says
Windows-1252, CR LF is LF, Ctrl+Z ends the file. `iswctype` is compared with the C
library for ASCII; above it only the no-break space has a class.

The opening and reading through `NtCreateFile` is exercised by `FOR /F` at step 6.
msvcrt no longer lacks anything cmd imports.

## Step 4

The 34 functions are in `user/win/kernel32/cmd_api.c`. The console is a terminal
speaking UTF-8 and ANSI sequences, so the console calls translate to it. Written
down because each is a limit a program can see:

- Local time is UTC, and the one locale is en-US.
- `SetConsoleMode` is accepted and not applied; text attributes do nothing.
- The screen buffer always says 80 by 25.
- `MoveFileExW` with replace deletes the target first, so it is not atomic.
- `CreateHardLinkW`, `CreateSymbolicLinkW`, `GetDiskFreeSpaceExW`,
  `GetVolumeInformationW` and `SetVolumeLabelW` fail with a Windows error.

They first ran with cmd itself, at step 6.

## Step 5

- `RtlGetVersion` answers Windows 10 build 19045, as the PEB does.
- `LoadStringW` reads the module's own `RT_STRING` resources. It used to fail
  always, and cmd takes every message it prints from there.
- `CharNextExA`, `IsCharAlphaNumericW` (ASCII and Latin-1).
- advapi32's three calls about a file's owner refuse: files have no security
  descriptor to hand out, and `DIR /Q` then shows no owner.
- `shell32.dll` is new: `FindExecutableW` knows only `.exe` and `.com`,
  `SHGetFileInfoW` tells a console program from a windowed one, and
  `SHFileOperationW` does the delete of `rmdir /s`, removing links without
  following them.

## Step 6

`scripts/dev/corpus-build.sh` builds `cmd.exe` from the pinned Wine source and the
image puts it in `C:\Windows\System32`. At boot it runs
`tests/corpus/cmd-check.bat`: variables, arithmetic, `if`, `for`, `goto`, `call`,
redirection, `FOR /F`, copy, move, delete, `rmdir /s` and a child `cmd`. The gate
compares its 40 lines with `cmd-expected.txt`, printed by the same `cmd.exe` under
Wine, and fails `cmd_script_differs`. An image without it says nothing unless the
corpus is required. Case: `cmd-boot.txt`.

What the first boots found:

- A process started from a Linux shell has a Linux `PATH` and no `PATHEXT`, so
  `cmd /c` from a batch file was not recognized. cmd's entry sets Windows' defaults.
- A directory listing is kept by position, so deleting while walking skips entries
  (WO-107). `rmdir /s` asks for the listing again after each removal.
- cmd ended with an access violation twice, on `if exist "dir\nul"` after a failed
  `rmdir` (WO-108). The same lines ran clean on other boots; the cause is not known.

The console calls are not proved by this boot: making `WriteConsoleW` write nothing
left the gate green, so cmd's output there takes another path. They need a test at
a terminal, which S7 will be.

windres warns about two strings of `cmd.rc` written for Wine's own resource
compiler, so those two messages may read slightly differently.
