# S7: FinalCommander

Phase S7 of the shell ([design.md](design.md)): FinalCommander, an orthodox
two-panel file manager for the terminal (Rust, MIT), as the workload that proves
the console, the pseudo-terminal and both personalities at once.

| Step | What | State |
|---|---|---|
| 1 | The Linux build at boot, driven at a pseudo-terminal | done |
| 2 | Loading a large program without reading all of it first | done |
| 3 | The Windows build, `fcmd.exe`, through the NT personality | to do |

## Where it comes from

The release binaries of v0.46.1, not a build: no Rust toolchain is assumed here.
`scripts/dev/corpus-build.sh` fetches them by the sums in `tests/corpus/sources.txt`,
which are the ones the release publishes in its `SHA256SUMS`. The source is the
submodule `third_party/FinalCommander`, at the same tag, to read them against. An
image built without the corpus has no `fcmd`; a job that requires the corpus
fails `corpus_program_absent:fcmd`.

## Step 1

`tests/linux/musl_fcmd.c` plays a person at a pseudo-terminal: it opens a
directory holding a file with a known name, waits for the panel to show it, makes
a directory with F7, checks on the disk that it exists, and quits with F10. It
runs on Linux and at every boot that has `fcmd`; the gate fails `fcmd_failed:<which>`.
Case: `fcmd-boot.txt`.

What its first boots found:

- **A position-independent program larger than the low window was refused.** Linux
  programs are placed at 0x400000, in an 8 MiB window, and `fcmd` spans 25 MiB. A
  PIE runs wherever it is put, so one that does not fit is now placed at +256 GiB
  in the high window, above the stack, the break and the mmap area.
- **It takes about a minute to start.** Exec maps every page of the image before
  the program runs, and reads each one through the page cache: 6,300 reads for
  this program. The test prints a line every ten seconds meanwhile, or the gate
  takes the quiet for a wedge. Step 2 is about this.
- The name and Enter have to be typed as two writes: in one, the program takes the
  whole as a paste.

## Step 2

Exec no longer maps a high-window program's read-only file pages: it records a
region for each (`VIBEOS_BACKING_FILE`, `DEMAND`), and the page fault maps the
page cache's own page the first time it is touched. On the first boot, 6,108 of
fcmd's pages were deferred and 865 were ever touched. The gate reads
`pages_file_deferred` and `pages_file_faulted` and fails
`exec_file_pages_not_deferred` if either is zero. Case: `exec-file-deferred-boot.txt`.

That alone took the start from about 64 seconds to 27, and the guess for the
rest - one region per page, 6,300 inserts into a sorted list - was wrong. The
wedge report put the one busy core in `virtio_blk_rw_n`: `hw_read_file_cached`
walked every page of the file into the cache whatever window its caller asked
for, so exec still read all 25 MiB, a page at a time. It stops at the caller's
window now, and the whole test - exec, panel, F7, F10 - takes under ten
seconds. The low window keeps the old way: it lies over the kernel's identity
map, where a page nobody mapped is present for ring 0.
