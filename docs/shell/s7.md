# S7: FinalCommander

Phase S7 of the shell ([design.md](design.md)): FinalCommander, an orthodox
two-panel file manager for the terminal (Rust, MIT), as the workload that proves
the console, the pseudo-terminal and both personalities at once.

| Step | What | State |
|---|---|---|
| 1 | The Linux build at boot, driven at a pseudo-terminal | done |
| 2 | Loading a large program without reading all of it first | done |
| 3 | The Windows build, `fcmd.exe`, through the NT personality | to do |
| 4 | Seeing it: the panels in the VM, and the console that draws them | done |

## Where it comes from

The release binaries of v0.46.1, not a build: no Rust toolchain is assumed here.
`scripts/dev/corpus-build.sh` fetches them by the sums in `tests/corpus/sources.txt`,
which are the ones the release publishes in its `SHA256SUMS`. The source is the
submodule `third_party/FinalCommander`, at the same tag, to read them against. An
image built without the corpus has no `fcmd`; a job that requires the corpus
fails `corpus_program_absent:fcmd`.

## Step 1

`tests/linux/musl_fcmd.c` plays a person at a pseudo-terminal: it opens a
directory holding a file with a known name, waits for the panel to show it, makes
a directory with F7, checks on the disk that it exists, and quits with F10. It
runs on Linux and at every boot that has `fcmd`; the gate fails `fcmd_failed:<which>`.
Case: `fcmd-boot.txt`.

What its first boots found:

- **A position-independent program larger than the low window was refused.** Linux
  programs are placed at 0x400000, in an 8 MiB window, and `fcmd` spans 25 MiB. A
  PIE runs wherever it is put, so one that does not fit is now placed at +256 GiB
  in the high window, above the stack, the break and the mmap area.
- **It takes about a minute to start.** Exec maps every page of the image before
  the program runs, and reads each one through the page cache: 6,300 reads for
  this program. The test prints a line every ten seconds meanwhile, or the gate
  takes the quiet for a wedge. Step 2 is about this.
- The name and Enter have to be typed as two writes: in one, the program takes the
  whole as a paste.

## Step 2

Exec no longer maps a high-window program's read-only file pages: it records a
region for each (`VIBEOS_BACKING_FILE`, `DEMAND`), and the page fault maps the
page cache's own page the first time it is touched. On the first boot, 6,108 of
fcmd's pages were deferred and 865 were ever touched. The gate reads
`pages_file_deferred` and `pages_file_faulted` and fails
`exec_file_pages_not_deferred` if either is zero. Case: `exec-file-deferred-boot.txt`.

That alone took the start from about 64 seconds to 27, and the guess for the
rest - one region per page, 6,300 inserts into a sorted list - was wrong. The
wedge report put the one busy core in `virtio_blk_rw_n`: `hw_read_file_cached`
walked every page of the file into the cache whatever window its caller asked
for, so exec still read all 25 MiB, a page at a time. It stops at the caller's
window now, and the whole test - exec, panel, F7, F10 - takes under ten
seconds. The low window keeps the old way: it lies over the kernel's identity
map, where a page nobody mapped is present for ring 0.

## Step 4: seeing it

The first look at FinalCommander in the VirtualBox image was two empty panels
saying "reading", drawn over each other in grey. Four things, none of them in
FinalCommander.

**The panels said "reading" for good.** FinalCommander runs on an asynchronous
runtime in the style of tokio: its workers park in `epoll_wait` on an eventfd,
edge-triggered, and are woken by a write to it that nobody ever reads. Linux's
edge-triggered epoll reports every such write; this kernel's reported a rise
from not-ready to ready, so from the second wake on nothing rose and the worker
holding the directory listing slept for ever. One boot in six of the gate's
`/tmp` panel lost the same race; the VM, slower and on `/root`, lost it every
time. A description now counts arrivals (`happened`, `vibeos_file_t`), the
eventfd's write counts one, and an edge-triggered entry reports its input again
when the count has moved (`kernel/abi/linux/epoll.c`; docs/abi/phases.md, L4
step 5). Host test "a second write into the readable eventfd is reported
again", case 12 of `abi-epoll.txt`. Found with `strace` on Linux: the trace
showed the workers' `epoll_pwait` and the writes to an eventfd with no read.

**The console drew a row up to its first empty cell.** A cell was a byte and a
row a C string, so anything a program wrote after an erase was never drawn.
A cell is a code point and two colours now (`kernel/io/gui.c`), every cell is
drawn, and an empty one is a background.

**The console understood six sequences.** The parser (`kernel/io/vt.c`) kept
two numbers and knew the cursor movements and three erases; an OSC was text
after its first byte, so the window title FinalCommander sets was printed on the
screen. It keeps sixteen numbers now and knows colours (16, 256 and 24-bit,
bold, reverse, underline), the alternate screen, a scroll region, inserting and
deleting characters and lines, absolute row and column, save and restore,
index, and swallows OSC, DCS and character-set designations. Queries - the
device attributes FinalCommander asks for, the kitty keyboard protocol - are
not answered: a program that waits for the answer waits out its own timeout.

**No UTF-8 and an ASCII font.** The parser decodes UTF-8 into code points (a
broken sequence is U+FFFD, and an escape that cuts one short is not lost). Box
drawing, U+2500 to U+257F, is drawn from lines - light, heavy and double, so
that a frame joins from cell to cell - and so are the block elements and the
ellipsis; arrows, bullets and quotes fall back to an ASCII stand-in, anything
else to `?`. Wide characters take one cell, which misaligns a row that has them.

The window is 120 columns by 36 rows for a program now (it was 71 by 24): two
panels side by side need it.

Host tests: `test_screen_full` in `tests/kernel/vt_tests.c`, including two that
read the framebuffer - a character past an erased cell is drawn, and a double
line runs across its cell. The GUI's torture now sends stray UTF-8 continuation
bytes where it sent raw high bytes, each one replacement cell. Cases:
`io-vt.txt` (four new), `io-gui.txt` (five new). The pixels as a whole are
still checked by eye, in the VM or with `scripts/dev/screenshot.py`.
