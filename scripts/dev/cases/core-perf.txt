# The performance ratchet, proven able to fire.
#
# docs/core/phases.md, C0: "a ratchet nobody has seen go red is a ratchet with
# no evidence behind it. Do that one first." This is that one.
#
# The boot gate ratchets syscall_min - the fastest observed syscall dispatch,
# the one number of the [PERF] line a blocked task cannot inflate - against a
# generous ceiling (5000 cycles under TCG; the minimum sits at 208-440). This
# case puts an unconditional spin inside the timed window of every dispatch, so
# even the fastest one clears the ceiling, and the gate must report
# perf_syscall_min_regressed rather than pass.
#
# Target source: kernel/arch/x86_64/arch_hw.c
# Run: SABOTAGE_VERIFY="<a boot-gate command that fails on a perf regression>" \
#      python3 scripts/dev/sabotage.py kernel/arch/x86_64/arch_hw.c \
#              scripts/dev/cases/core-perf.txt
# It has also been confirmed by hand: the spin applied, built and booted, the
# gate reported perf_syscall_min_regressed and status=fail; reverted, green.
#
# This is the sabotage case for the whole [PERF] area, so it also names the
# other assertions that line carries, which have no separate case: a build that
# stops emitting the line at all trips perf_counters_missing; one that increments
# an event counter but never its cycle counter (half a measurement is worse than
# none) trips perf_syscall_cycles_never_accumulated or
# perf_fault_cycles_never_accumulated. The spin above exercises the ratchet;
# these are the same instrument's other failure modes, gated together here.
#
# The boot-wall-time ratchet (boot_wall_regressed) belongs to the same C0
# baseline: kernel_early_init to kernel_boot, ceiling 8s. It is loose by design
# (wall-clock seconds move with host load, unlike syscall_min's cycles), and was
# confirmed to fire by lowering the ceiling below the observed 1.1s on a normal
# boot - the gate reported boot_wall_regressed - rather than by delaying bring-up.
