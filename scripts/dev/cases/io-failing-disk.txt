# A disk that fails, swept across which request fails (I7, first item).
#
# Host tests: bash scripts/dev/check.sh tests build-gcc-Release
#
# Every other test of this layer asks what happens when the disk works. This
# asks what the layer promises when it does not, and the promise is three
# things at once - the caller is told it failed, the failure carries a reason,
# and nothing is left in flight. They are checked together because a layer can
# keep any two and break the third.

case: the layer stops comparing sectors_done against sectors
  in vibeos_blk_submit, replace the `req->sectors_done != req->sectors` test
    with `if (0)`
  expect: FAIL:blkfail "failed in the driver and the layer reported success"
  why it matters: this is the check the FAT defect needed. There, a failed
    table read came back as the end-of-chain marker and the reader returned the
    size the directory claimed - a short file that said it was complete. A
    driver that moves fewer sectors than asked and returns zero is the same
    failure one layer down, and it is silent, which makes it worse than an
    error.

case: a failure is returned with no reason recorded
  in vibeos_blk_submit, return -1 on a driver failure without the NOT_ISSUED
    fallback or count_result
  expect: FAIL:blkfail "the failure was counted under no reason"
  why it matters: "the disk is missing" and "the disk is broken" become one
    number, which is exactly what this layer was built to stop. A count with no
    reason is a count nobody can act on.

# The sweep is over three axes and each one earns its place:
#
#   which request fails - failing the first request of a run, one in the
#     middle, and one after successes are three different states of the layer's
#     own bookkeeping, and a single test picks one of them by accident;
#
#   how it fails - a driver that returns an error and a driver that returns
#     success having moved too little are different code paths, and the second
#     is the one that corrupts quietly;
#
#   how many sectors - a short transfer cannot be expressed by a one-sector
#     request, so a sweep over one size only would never construct the case it
#     was written for. That is the "right about the outcome, wrong about the
#     mechanism" trap, avoided by construction rather than by luck.
#
# Position 4 of the sweep fails nothing: a run in which the failure never
# happens is what proves the checks are not passing for the wrong reason.

# ---- what this does NOT cover, and is the rest of I7 -----------------------
#
# A failure *during* a multi-sector transfer that has already moved some
# sectors to the caller's buffer, a failure of the barrier rather than of a
# transfer, and a failure while another core is submitting to the same device.
# The last one needs the queue I6 introduces and cannot be written before it.

# ---- the rest of I7's first item -------------------------------------------

case: a partial transfer is not compared against what was asked for
  in vibeos_blk_submit, replace the sectors_done comparison with `if (0)`
  expect: FAIL:blkfail "failed in the driver and the layer reported success"
  why it matters: the device moved half the sectors into the caller's buffer
    and then gave up. The bytes that arrived are real and the rest are stale,
    and a caller told "success" has no way to tell which half is which. The
    test asserts both directions - that the failure is reported *and* that the
    sectors which did arrive are still there, because a layer that zeroed the
    buffer on failure would pass the first check while throwing away data the
    device had actually delivered.

case: a refused barrier is reported as granted
  in vibeos_blk_barrier, drop the check on the driver's return
  expect: FAIL:blkfail "a refused barrier was reported as granted"
  why it matters: the journal builds its entire recovery argument on the answer
    to this call. "Yes" when the device said no is the difference between a
    recoverable medium and a corrupt one, and nothing downstream can detect it.

case: the layer is re-entered while a request is in flight
  covered by test_bf_reentrant_submit, which submits from inside the driver
  expect: the outer request still describes its own transfer and gets its own
    data
  NOTE, and it is a real limit: this is re-entrancy, not concurrency. A host
    test has one thread. What it reproduces is the same globals touched in the
    same order while an earlier request is unfinished, which is the shape of
    another core submitting - but it cannot produce two cores genuinely inside
    the layer at once. That needs the boot, and it is the part of I7 that stays
    open. The test guards against passing vacuously: it fails if the re-entrant
    submit never actually happened.
