# Sabotage cases for the filesystems that had never run (I5).
#
# Run: apply the edit, bash scripts/dev/check.sh build <dir>, then
#      python3 scripts/qemu-cli-smoke-linux.py <dir> 300

case: a filesystem stops being exercised
  in arch_hw.c, remove the iso9660 row from g_fsimages
  expect: fsimage_missing:iso9660
  why it matters: these drivers existed for months and had never parsed
    anything. A boot that stops exercising one puts it straight back in that
    state, and the way it got there was nobody noticing.

    The gate lists the expected names rather than counting them, because a
    count cannot tell "iso9660 stopped running" from "ext2 ran twice". That is
    also why the bring-up is a table: a second copy of the function with four
    names changed is how a family ends up with one member asserted.

case: the ISO9660 logical block size is read as a 32-bit field
  in kernel/fs/iso9660.c, put rd32le back at offset 128
  expect: iso9660:FAILED:_mount, and FAIL:test_iso_refusals in the host tests
  why it matters: this was the real defect, and it is the whole argument for
    the phase. The field is a both-endian *16-bit* pair; a 32-bit little-endian
    read of it returns 0x00080800 for the 2048 every ISO uses, so the mount
    refused every image ever made. The host test could not see it because the
    fixture wrote the field the same wrong way - driver and fixture agreed with
    each other for months. Both were fixed, and the corrected fixture was
    confirmed to go red against the old driver before the driver was touched.

case: the image is built by this project instead of by mke2fs
  in scripts/make-fs-image.py, write the superblock by hand
  expect: NOT A CASE TO RUN - it is the case the design exists to avoid.
    An image this project wrote would only prove the driver and the writer
    agree with each other. The whole value of shelling out to the host's mkfs
    is that it is the one artefact neither side of this test controls.

case: the loop device serves a fragmented file
  in vibeos_x86_64_loop_attach, drop the !contiguous refusal
  expect: NOT OBSERVABLE ON THIS MEDIUM, where the staged image comes out as
    one run. It is the most dangerous path here: a loop device that spanned a
    gap would present another file's bytes as part of the filesystem it is
    mounting, and the driver above would parse them - which is a mount that
    succeeds and is wrong. Reproduce by fragmenting EXT2.IMG on the medium.

case: the loop device accepts a write
  in loop_submit, perform the write instead of refusing it
  expect: nothing on a healthy boot, because nothing writes to it
  why it matters: a device that accepts a write it does not perform tells the
    caller the bytes are safe. The refusal is what makes "read-only" a fact
    rather than a convention.

case: the marker file is a constant instead of carrying its offset
  in make-fs-image.py, fill content() with one byte value
  expect: the test still passes, and stops being able to fail
  why it matters: a constant survives a read that returned the wrong block, as
    long as that block had been written too - which for a file that fills
    several blocks is exactly the interesting failure.

case: NTFS or exFAT stops being exercised
  in arch_hw.c, remove that row from g_fsimages
  expect: fsimage_missing:ntfs  /  fsimage_missing:exfat
  why it matters: same reason as the first case in this file. Both drivers had
    been in the tree for months without ever parsing a byte.

case: exFAT is reported OK when it only mounted
  in hw_fsimage_bringup, report "OK" instead of "OK (no marker)" for a row
    with no marker
  expect: nothing turns red, and that is exactly why the distinction exists
  why it matters: exfatprogs ships no tool that writes into an image without
    mounting it, and mounting needs root and FUSE - which neither a developer
    machine nor a CI container reliably has. So the exFAT image carries no file
    to read back, and the verdict says so. "Mounted a real volume" and "mounted
    a real volume and read a file out of it" are different claims, and folding
    the weaker one into the stronger is how a gap stops being visible. If a
    tool ever appears that can stage into exFAT offline, this row gets a marker
    and this case disappears.

case: the NTFS marker is written by mounting the image
  in make-fs-image.py, replace ntfscp with mount -o loop
  expect: it works as root and fails everywhere else
  why it matters: an image staged through `mount` is staged by the host
    kernel's driver, which is a different objection from needing root. The
    point of building these images with somebody else's mkfs is that no part of
    the artefact comes from a driver either side of the test controls. ntfscp
    writes into the image directly, which keeps that property and needs no
    privileges.

case: the NTFS index allocation is never walked
  in ntfs_index_scan, return 0 as soon as the root misses
  expect: ntfs:FAILED:_read on the gate, and the host tests STAY GREEN
  why it matters: this is the case that justifies the whole phase in one line.
    It is the driver's original behaviour: it refused any directory with an
    $INDEX_ALLOCATION, which reads like a large-directory limitation and is
    not - mkntfs gives the *root* directory one, because a fresh volume already
    holds sixteen metadata files. So the driver could not read a single real
    NTFS volume, and the host test could not tell, because its synthetic image
    was the one shape the driver could handle. Only the image built by mkntfs
    catches it.

case: the index walker reads its offsets from the attribute instead of the header
  in ntfs_index_walk, restore `off = 16u + rd32(base + 16)`
  expect: FAIL:test_ntfs_list
  why it matters: that is the mistake actually made while extracting the walker
    so the root and an INDX block could share it, and the existing host test
    caught it on the first run. Worth recording as the case where the synthetic
    fixture *was* the right tool: a refactor that breaks the shape the fixture
    covers is exactly what it is for.

case: INDX fixups are not applied
  in ntfs_index_scan, skip the ntfs_apply_fixups call on an index block
  expect: ntfs:FAILED:_read, or a malformed-node refusal
  why it matters: the last two bytes of every sector of an INDX block are a
    sequence number, and the real bytes live in an array at the front. A reader
    that skips the substitution gets two wrong bytes every 512, which here land
    in the middle of entry lengths - so the walk does not fail, it walks into
    the wrong place.
